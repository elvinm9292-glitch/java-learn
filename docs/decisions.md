# Принятые решения

Формат: решение — почему — что отвергли.
Это материал для собеседования: ценно не «я сделал», а «я выбрал, потому что».

---

## Баланс меняется только операциями

Поле `balance` убрано из DTO создания и изменения счёта, `PUT /accounts`
меняет только `owner`.

Почему: иначе одним HTTP-запросом можно поставить себе любой баланс без
единой проводки. При ночной сверке деньги появятся из воздуха, и объяснить
их происхождение будет нечем. Плюс бытовой случай: форма «изменить владельца»
не присылает `balance`, в DTO приходит `null`, баланс стирается.

---

## IBAN выдаёт банк, а не клиент

Поле `iban` убрано из запроса на создание. Номер генерируется в
`AccountService`.

Почему: если номер присылает клиент, он может прислать чужой.
В настоящем банке номер счёта назначает банк.

---

## Номер счёта — из последовательности базы, не случайный

`CREATE SEQUENCE account_number_seq`, значение дополняется нулями слева
до 20 знаков: `AZ` + `00` + `NABZ` + 20 цифр = 28 символов.

Почему: последовательность гарантирует отсутствие повторов самой базой,
без проверок в коде. Проверка `existsByIban` от гонки не спасает — между
проверкой и вставкой есть зазор.

Что отвергли: случайные цифры. Непредсказуемее, но требуют защиты
от совпадений.

Известный минус: при откате транзакции номер всё равно расходуется,
в нумерации появляются дырки (15, 16, 18). Это нормальное поведение
последовательностей, а не поломка.

---

## Контрольные цифры IBAN — заглушка `00`

Почему: учебный проект, вычисление по ISO 13616 сейчас не окупается.
Отмечено в README как осознанное упрощение.

Последствие, которое надо знать: настоящая внешняя система такой номер
отвергнет как некорректный, потому что эти две цифры — контрольная сумма,
и её все пересчитывают сами.

---

## Структура — модульный монолит, не микросервисы

Пакеты по функциональности: `account/`, `transaction/`, `common/`,
внутри каждого свои слои.

Почему: одно приложение, один процесс, одна база — это не микросервисы.
Нарезка по доменам нужна, чтобы при необходимости модуль можно было
отделить в отдельный сервис.

---

## Номер карты и CVV хранятся как есть

Почему: учебный проект.

В README отметить: в настоящем банке номер карты шифруется, а CVV
не хранится вообще — ни в каком виде.

---

## Журнал операций — строка на каждый счёт со знаком (двойная запись)

Две таблицы: `operation` (одна строка на операцию: тип, время) и
`ledger_entry` (строка на каждый затронутый счёт, сумма со знаком).
Перевод 100 — две строки: −100 и +100. Сумма строк одной операции всегда 0.

Почему: любое движение денег — «со счёта на счёт», даже покупка и пополнение
наличными (второй счёт — банковский: касса, транзит, доходы). Перевод
с комиссией затрагивает три счёта (−101, +100, +1) — одной строкой
«откуда, куда, сколько» его не записать, комиссия прячется внутри числа.
Выписка — `WHERE account_id = ?`, баланс для сверки — `SUM(amount)`.

Что отвергли: одна строка `from, to, amount`. Проще, но не выдерживает
комиссию и делает выписку запросом с `OR` по двум колонкам.

Записи журнала пишет только сервис внутри той же транзакции, что меняет
баланс. Эндпоинта «создать запись» нет — иначе журнал можно подделать.
Правило «сумма = 0» проверяется в `Operation`, не в базе.
